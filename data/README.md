# Data

## Source

The project uses PaySim, a synthetic mobile money transaction log generated by an agent-based simulator calibrated on one month of real transaction records from a mobile money service operating in an African country (Lopez-Rojas et al., 2016). The public release is distributed on Kaggle as `ealaxi/paysim1`.

| Property | Value |
|---|---|
| File | `PS_20174392719_1491204439457_log.csv` |
| Rows | 6,362,620 |
| Columns | 11 |
| Time index | `step`, one step per simulated hour |
| Positive class | `isFraud = 1` (8,213 rows, about 0.13%) |

The raw file is not tracked in this repository because of its size and license terms.

## Download

With the Kaggle CLI configured (`~/.kaggle/kaggle.json`):

```bash
kaggle datasets download -d ealaxi/paysim1 -p data/raw --unzip
```

Alternatively, download the archive from the Kaggle dataset page and extract it so the file sits at:

```
data/raw/PS_20174392719_1491204439457_log.csv
```

The original notebook in `notebooks/00_original_exploration.ipynb` reads from the Kaggle kernel path `/kaggle/input/paysim1/`. Change the path in its second cell when running it locally.

## Versioning

The raw file is identified by its content rather than tracked with a data-versioning tool. PaySim is one immutable public CSV, so DVC or a similar system would add a remote cache and pipeline definitions without adding information. After the first download, record the file's identity with

```bash
fraud-detection data pin      # or: make data, which downloads and pins
```

This writes `data/PS_20174392719_1491204439457_log.manifest.json`, which is committed. It holds the SHA-256 digest $h(D)$ of the file $D$, its size in bytes, and its numbers of rows and columns. `pin` warns if the shape differs from the public release (6,362,620 rows, 11 columns) and refuses to replace a manifest that pins different contents unless `--force` is given.

On any later run, `fraud-detection data verify` (or `make data-verify`) recomputes $h(D)$ and fails on any difference. `fraud-detection train` performs the same check whenever a manifest exists and writes the digest to `metrics.json` as `data_sha256`; tracked runs also carry it as an MLflow tag. Every reported metric can therefore be traced to the exact bytes it was computed from. A run on a modified or truncated file fails instead of silently producing numbers that are not comparable.

Runs on synthetic data (`--synthetic-rows`) are marked with `synthetic_data: true` and have no digest.

## Directory conventions

| Directory | Contents | Tracked |
|---|---|---|
| `data/raw/` | Files exactly as downloaded | No |
| `data/interim/` | Intermediate outputs such as typed Parquet copies | No |
| `data/processed/` | Model-ready feature tables | No |

Unit tests and CI do not depend on the real dataset. They use a synthetic generator that reproduces the PaySim schema and its main fraud mechanics.

## Notes on the simulation

Fraudulent transactions in PaySim occur only in the `TRANSFER` and `CASH_OUT` types and follow a fixed pattern: an account is taken over, its balance is transferred to a mule account, and the mule cashes out. The `isFlaggedFraud` column is a simple rule that marks transfers above 200,000 and fires on very few rows. Balance columns for merchant destinations (`nameDest` starting with `M`) are always zero. These properties should be kept in mind when interpreting feature importance, since a model can learn simulator artifacts that would not transfer to production data.
